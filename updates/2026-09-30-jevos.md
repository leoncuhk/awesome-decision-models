# jevos contribution review September 2026

[Home](../README.md) · [Source register](../docs/sources.md)

PR #1 adds a useful CPU-local yes/no baseline and discloses the submitter's affiliation. Maintainer review on 2026-09-30 retains that contribution and qualifies its provenance and API compatibility. No model inference or SDK conformance test was run.

The [submitted README](https://github.com/feder-cr/jev/blob/eb74cf78e5377e85fcaa76f6ebc9f82e8b517250/README.md) reports 0.815 for jevos and 0.927 for hosted Jev on 2,000 policy questions. Both are the project author's comparison, not a vendor-certified or independently reproduced result. The old release URL returned HTTP 404; its submitted hash remains in the historical source note.

The [v2 release](https://github.com/feder-cr/jev/releases/tag/jevos-v2), published September 29 UTC, separately reports 0.795 on 999 hand-written questions, compared with 0.757 previously. These figures use a different test from the README comparison. GitHub asset metadata gives a new q4 hash, recorded in the model card; the binary was not downloaded or hashed here. No earlier score is reassigned to v2.

The [pinned documentation](https://github.com/feder-cr/jev/tree/9e7d9e8a24e9605bec249045a39df91ff2b58b0d) describes a 1B model, CPU deployment and yes/no responses. It says `criteria` is accepted but ignored for jevos, and `choice`/`score` are refused. Applications must put their policy in `instructions` and check semantics rather than assuming that changing the endpoint is sufficient. The submitter's MiniCPM5 and 17-layer claims were not established by the reviewed public material, so the catalog leaves those details unresolved. Repository MIT licensing is distinct from base-weight provenance.

This changes the suggested experiment: test local reading/triage with labeled business cases and explicit error costs; compute dates and arithmetic in code. It does not establish a production recommendation, calibrated risk bound or common leaderboard.
