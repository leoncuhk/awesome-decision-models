# P08 技能与路径的动态加载

成熟度：**有据** · 层：系统集成 · 落地：[skill 路由选择器](../playbooks/skill-routing.md)

## 问题

服务 Agent 有几十个技能或流程时，每轮先选出一小组再交给执行器，是否优于全部暴露？这个选择器应该用什么、怎么训练？

## 当前判断

1. **要防的是选错，不是上下文太长。** 技能之间的相似度比数量更伤，技能粒度是首要设计变量。
2. **动态加载改变了错误类型**：全量暴露的问题是被稀释；动态加载的问题是被截断——加载器漏掉正确技能，下游无从挽回。主指标是带回退路径的 recall@k（漏检率），不是 top-1。
3. **路由只能拿到部分收益**：先用理想路由（oracle）量出上限，再优化路由器。
4. **护栏不能依赖路由**：红线、升级规则、身份核验放在常驻核心里，由代码强制。
5. **决策模型是候选选择器，不是默认选项**：小型监督分类器是必须打败的基线。

置信度：中。

## 证据

- 技能库扩到 202 个时，通过率最多下降 21%，其中最多 68% 来自选错技能；上下文开销的效应与零无法区分（[Databricks 2605.24050](https://arxiv.org/html/2605.24050)）。
- 技能池从 5 扩到 100，使用精度 29.6% → 3.3%；有相似干扰项时，嵌入检索 top-1 70.5% → 53.4%（[2608.14036](https://arxiv.org/html/2608.14036v1)）。
- 渐进披露在 100 个技能时恢复到 0.79–1.00（[Workday 2609.35692](https://arxiv.org/html/2609.35692v1)）；检索加离线意图查询，457 个工具时从 38.5 回升到 79.4（[Toollery](https://arxiv.org/pdf/2609.22218)）。
- 本仓收录的客服生产数据案例（Wix，75.7 万条消息）：状态谓词门控剔除 59.4% 候选；全量暴露时，7.8% 的选择会选中生产环境本应拦截的技能（[2608.01050](https://arxiv.org/pdf/2608.01050)）。
- 即使直接给定正确技能，最佳模型通过率也只有 45%（[Dialpad 2610.14346](https://arxiv.org/html/2610.14346)）。
- 技能作者自己写测试查询，会让 hit@5 虚高 21–44 个百分点（[Praetorian 2608.06196](https://arxiv.org/html/2608.06196)）。
- 多领域组合可能完全崩溃（[T1-Bench](https://arxiv.org/html/2606.11070v1)）；中途切换目标后的恢复率在 92.2%–48.6% 之间（[AgentChangeBench](https://arxiv.org/html/2510.18170)）。
- 拒判在近似选项下崩溃（[E20](../docs/evidence.md#e20)）；Jev 层级路由两步联合正确 404/600（[2610.00346](https://arxiv.org/html/2610.00346v2)）。

## 开放

- 中文客服约 40 个技能时，理想路由相对全量暴露的质量差距有多大？成本收益在开启提示缓存后还剩多少？
- 选择器用什么：检索、监督 encoder、决策模型 LoRA，还是托管 decision API？
- 带滞后的逐轮路由，能否处理话题切换？

本轮未确认可直接替代目标企业数据的中文、多技能、带政策客服基准，决定性实验必须用企业自己的流量。完整假设 H1–H6 与分阶段方案见 [playbook](../playbooks/skill-routing.md)。

## 企业含义

技能少、相互区分清晰时先以全量暴露作基线；不存在已验证的通用10技能分界。规模更大时，按“检索召回 → 状态门控 → 判断器 → 常驻核心”的顺序搭建，并以理想路由作为参照。
